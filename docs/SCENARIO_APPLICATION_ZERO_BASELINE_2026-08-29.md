## 1. 決策摘要

現有場景能力不是全部推倒重做。正確做法是：

1. 保留已經建立且可重用的資料模型、權限、任務、表單、簽核、Evidence、語音與掃碼能力。
2. 將目前分散在「現場作業、表單、審核、問答、師傅經驗」的介面重新組合成完整工作旅程。
3. 第一輪只把少數高價值場景做深；其他能力保留，但不要同時以半成品形式曝光給第一個租戶。
4. 場景是否顯示，必須由租戶啟用的 Pack、職能、權限與成熟度共同決定。
5. 採購、拜訪與請款目前只有表單骨架，不應對外宣稱為完整應用。

本文件中的分類是產品決策，不是刪除程式碼的指令。

## 2. 什麼才算一個完整場景應用

一張可以填寫的表單，不等於一個完整場景。完整場景至少要回答：

- 誰在什麼時候進入？
- 使用者要完成什麼工作？
- 系統能從文件、語音、照片、影片、掃碼或既有資料帶入什麼？
- 缺少哪些資料時，系統如何引導補齊？
- 哪些欄位是 AI 建議，哪些是正式來源，哪些必須人工確認？
- 完成後產生什麼結果？
- 是否需要送審、退回、追蹤或通知？
- 如何回到正式 SOP、規格或原始證據？
- 手機、平板與桌機的操作是否符合實際工作環境？
- 成效如何量測？

因此，場景成熟度採以下四級：

| 等級 | 定義 |
|---|---|
| S0 零件 | 只有 Schema、API、資料模型或局部元件。 |
| S1 可操作 | 有入口，可以完成單次填寫或查詢。 |
| S2 完整旅程 | 入口、引導、補件、送審、結果及後續追蹤已串成一條路。 |
| S3 租戶可交付 | 通過目標職能、真實資料、裝置、權限、例外與驗收指標測試。 |

目前大多數應用介於 S0–S1；核心知識問答及部分知識治理能力較接近 S2，但仍需由真實租戶驗證才能成為 S3。

| 新人訓練 | `training` 任務、訓練檢核表 | S1 | **與知識傳承整合重做** | 應從職務必讀、情境題、實作確認與進度出發，不只是 checklist。 |

## 4. 建議的產品場景組合

### 4.1 核心產品：知識工作台

所有租戶共同擁有，不屬於 MKA 選配場景：

```text
匯入／錄製／拍攝
  → 自動解析與品質判斷
  → 人工覆核與正式發布
  → 搜尋／問答／引用
  → 回饋與知識修訂
```

核心入口應圍繞使用者目的，而不是技術名詞：

- 找答案
- 加入資料
- 處理待確認內容
- 管理正式知識

規格、SOP、制度、設備手冊、老師傅知識，都應透過同一套搜尋與 Evidence 體驗被使用，再由篩選條件與職能決定範圍。

### 4.2 第一優先 Pack：現場事件與交接

把目前的異常回報、設備維修、交接班與工作日報重組為一條事件旅程：

```text
掃設備 QR／直接說話／拍照
  → 辨識廠區、產線、設備與異常描述
  → 先顯示安全提醒及適用 SOP
  → 建立異常事件
  → 指派或記錄處置／維修
  → 交接未完成事項
  → 自動彙整班報／日報
  → 關閉事件並沉澱案例知識
```

這個設計能避免同一件事情被重複填入四張表單，也最能展現本產品的 Input 與知識庫優勢。

### 4.3 第一優先 Pack：知識傳承與新人上手

把訪談建卡、師傅經驗庫、新人訓練與 SOP 衝突覆核組成閉環：

```text
長時間錄音／影片／現場訪談
  → 逐字稿、步驟、判斷、風險與例外候選
  → 師傅或主管逐項確認
  → 與正式 SOP 比對
  → 發布成有證據與版本的知識單元
  → 指派給特定職務新人
  → 情境題、實作確認與進度追蹤
  → 現場回饋回到修訂流程
```

這個 Pack 是多模態 Input 與企業知識核心最具差異化的應用，建議與現場事件並列第一優先。

### 4.4 第二波 Pack：品質問題與改善

重組異常、8D、CAPA 與效果驗證：

```text
品質問題／客訴
  → 影響與圍堵
  → 證據、規格及歷史案例
  → 根因分析
  → 改善措施、責任人與期限
  → 核准
  → 成效驗證
  → 正式結案與知識回饋
```

品質 Pack 應共用「現場事件」，不能另造一份重複的異常資料。

### 4.5 候選 Pack：報價與產銷協作

現有報價能力先保留。正式產品化前，需先確認首租戶是否具備：

- 可讀取的客戶、料號、歷史價格、MOQ 與交期資料。
- 價格及折扣權限。
- 公司正式報價版型。
- 報價核准層級。
- 是否需要寫回 ERP 或僅匯出文件。

若資料條件不足，報價很容易退化成另一張需要人工重填的電子表單，不應優先於知識傳承或現場事件。

## 5. 建議暫時不作為主要產品入口的功能

以下能力不刪除，但在沒有租戶明確需求前，不放入預設首頁或主要導航：

- 採購單。
- 請款單。
- 會議／拜訪紀錄。
- 獨立的 CAPA 表單入口。
- 獨立的設備維修表單入口。
- 以「所有表單種類」為起點的表單目錄。

理由不是它們沒有價值，而是目前尚未形成足以交付的完整工作旅程。過早曝光會使產品看起來像功能很多但彼此鬆散的表單集合。

## 6. UIUX 歸零後的資訊架構原則

### 6.1 不再以內部架構名稱要求使用者理解產品

使用者不需要理解 Asset、Task Definition、Form Instance、Module Binding 或 Pack。這些保留在系統底層與管理介面。

一般使用者的一級入口建議收斂為：

| 使用者心智 | 入口內容 |
|---|---|
| 首頁／今天 | 我的待辦、待審、進行中事件、最近工作。 |
| 問知識 | 搜尋、提問、證據、追問與回饋。 |
| 開始工作 | 依職能顯示可啟動的少數場景。 |
| 知識 | 已發布內容、我建立的內容、待覆核內容。 |

管理者才需要看到：資料來源、Input 品質、權限、模組、職能、模板、治理、稽核與系統健康。

### 6.2 以事件與工作為中心，不以表單為中心

表單是保存結構化結果的機制，不是使用者旅程本身。

例如使用者點「回報設備異常」後，可以說話、拍照或掃碼；系統逐步確認必要資料，最後才形成異常單。使用者不必先理解要去哪一張表、哪些欄位能由系統自動帶入。

### 6.3 一個場景只提供一個主要入口

- 規格／SOP 查詢進入「問知識」，不另設近似問答頁。
- 訪談建卡從「建立知識」開始，不在任務頁與 Know-how 頁各有一套流程。
- 8D 與 CAPA 從同一品質事件開啟，不暴露兩張孤立表單。
- 異常、維修、交接與日報共用同一事件紀錄。

### 6.4 AI 建議與正式事實必須視覺分離

每個高風險場景都應清楚顯示：

- 系統自動辨識的內容。
- 來自正式文件或外部系統的資料。
- 使用者手動修改的內容。
- 尚未確認的低信心欄位。
- 必須由誰核准。

### 6.5 依工作環境設計裝置體驗

- 現場：大按鈕、單手操作、語音、拍照、掃碼、可中斷續填、弱網處理。
- 主管：桌機或平板待辦、差異比較、風險排序、批註與退回。
- 知識管理者：證據並排、低信心內容、版本差異與批次處理。
- 新人：簡潔閱讀、情境問題、逐步檢核與求助入口。

## 7. 建議實作順序

### R0：先收斂，不改底層契約

- 建立場景 feature flag 與成熟度標記。
- 預設隱藏 S0 場景。
- 將「我的表單」與「審核」重新定義為跨場景待辦能力。
- 建立共用事件、附件、Evidence、責任人、期限與狀態的畫面契約。

### R1：重做現場事件與交接

- 單一事件入口。
- 語音、拍照、影片、QR 與手動輸入。
- 安全提醒、SOP 與歷史案例。
- 異常、處置、維修、交接、日報資料不重複輸入。
- 手機／平板優先。

### R2：重做知識傳承與訓練

- 訪談／錄音／影片匯入。
- 多模態萃取與時間碼證據。
- 人員覆核與 SOP 衝突處理。
- 發布、指派、學習與現場回饋閉環。

### R3：重做品質 8D／CAPA

- 從事件建立品質案件。
- 多角色協作、期限與成效驗證。
- 將改善成果回寫為案例知識。

### R4：依首租戶資料條件決定報價產品化

- 先完成資料契約與整合可行性。
- 再設計報價旅程、核准與正式輸出。

每一階段都必須先完成 code review、角色走查、權限測試、異常路徑測試及最小瀏覽器驗收，才進入下一階段。

## 8. 首租戶建議開放範圍

第一個租戶不建議一次開放所有 MKA 功能。建議選擇以下其中一個主場景：

1. **知識傳承與 SOP 問答**：風險相對可控，最能驗證 Input、知識庫與 Evidence。
2. **現場異常與交接**：價值容易量測，但需更完整的裝置、弱網、安全與流程驗證。

預設共同提供：

- 多元 Input。
- 知識資產與審核。
- 有證據的問答。
- 權限與版本治理。
- 單一試行場景。

其他場景保持停用，直到完成租戶資料契約、角色流程及驗收標準。
