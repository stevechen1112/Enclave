## 0. 目的與使用方式

本劇本服務四個目的：

1. **找功能卡點**：每個任務標註對應系統功能，壞掉、缺資料、回錯誤直接對應工程 backlog。
2. **找選單／導覽問題**：用 §2 的角色 × 選單矩陣**逐項點完所有選單**，找出死路、權限破口、命名不清、空狀態無引導等問題。
3. **找 UIUX 問題**：用 §3 的十項體檢維度檢查每個頁面與每個任務。
4. **沉澱 DEMO 素材**：§8 附每線 5 分鐘精華版。

### 0.1 三個測試角色

| 代號 | 角色 | 系統角色（role） | 對應職能 | 主要模組 |
|------|------|------------------|----------|----------|
| A | 業務／業務助理 | `employee` | `sales` | 業務報價（`sales_quote`）、規格與 SOP（`spec_sop`） |
| B | 設備與現場人員 | `employee` | `equipment`（任務 applicable 亦接受別名 `field`） | 現場異常與交接（`incident_handover`）、規格與 SOP |
| C | 資深師傅／訓練負責人 | `employee`（師傅）＋ `owner`（主管） | `master`／`newcomer`／`supervisor` | 知識傳承與訓練（`training_knowhow`） |

> 另備 1 組 `viewer` 帳號，專門用於 §2.3 權限邊界測試。

### 0.2 執行方式

- 每角色 **3–5 位**真實使用者（內部同仁第一輪，Design Partner 第二輪）。
- **放聲思考法**：主持人不教學，只給任務卡；觀察員記錄 §9 記錄表。
- 每場 60–75 分鐘：5 分鐘說明 → **10 分鐘選單自由探索（§2）** → 30–40 分鐘任務 → 10 分鐘訪談。
- 主持人必備：測試帳號、任務卡、計時器、記錄表、錄影（取得同意後）。

### 0.3 卡點嚴重度分級

| 等級 | 定義 | 處理 |
|------|------|------|
| P0 | 任務無法完成／資料錯誤／權限或安全問題 | 擋下，修完才繼續測 |
| P1 | 能完成但需繞路、求助、或重試 2 次以上 | 列入近期修正 |
| P2 | 不順但不影響完成（文案、位置、回饋不明確） | 列入優化清單 |

## 2. 選單功能地毯式檢查（每場必做，10 分鐘）

> 目的：在使用者執行任務**之前**，先讓他自由探索選單，量測「資訊架構是否直覺」；之後主持人再帶 §2.2 的逐項檢查。

### 2.1 自由探索（使用者主導，5 分鐘）

**任務卡**：「先不做任何指定工作。請隨意點開你看到的每個選單，邊點邊說你覺得這裡面是什麼。」

記錄：
- 使用者**以為**每個選單裡是什麼 vs 實際是什麼（命名落差）
- 哪些選單使用者完全沒興趣點（可能是命名無意義）
- 使用者想找「報價／異常／知識卡」時，**第一個點的選單**是哪個（驗證心智模型）

### 2.2 角色 × 選單逐項檢查（主持人帶領，5 分鐘）

依登入角色逐項點開，每項檢查四件事：**① 看得懂名稱 ② 點進去有內容或明確空狀態 ③ 返回路徑直覺 ④ 不該看到的人看不到**。

#### 員工角色（employee：業務 A／現場 B／師傅 C 適用）

| # | 選單 | 路由 | 檢查點 |
|---|------|------|--------|
| E1 | 現場作業（預設首頁） | `/job` | 登入是否直接落在此頁？工作台入口是否依職能不同而不同？入口名稱是中文動作（「開報價單」）還是系統術語？ |
| E2 | 問答 | `/ask` | 與「現場作業」裡的提問入口有何差異？使用者分得清楚嗎？從模組入口帶 `?module=` 進來時有無場景提示？ |
| E3 | 知識 | `/knowledge/documents` | 員工看到的是文件清單；是否誤以為可以上傳（無權限時按鈕應隱藏或禁用，而非點了才報錯）？ |

#### 主管／管理員角色（owner/admin，劇本 C 主管與管理情境適用）

| # | 選單 | 路由 | 檢查點 |
|---|------|------|--------|
| M1 | 總覽 | `/overview` | 儀表數字看得懂嗎？有無「需要我處理的事」明確呈現？ |
| M2 | 現場作業 | `/job` | 主管的工作台是否包含審核待辦？ |
| M3 | 問答 | `/ask` | 同 E2 |
| M4 | 知識 → 文件／知識頁 | `/knowledge/documents`、`/knowledge/wiki` | 文件狀態（處理中／完成／失敗）是否可讀？ |
| M5 | 知識 → 來源 | `/knowledge/sources` | 連接器狀態非工程師看得懂嗎？ |
| M6 | 知識 → 審核 | `/knowledge/review` | 與 MKA 審核收件匣（`/approvals`）的差異，使用者會混淆嗎？（**已知風險點：兩處「審核」**） |
| M7 | 知識 → 品質 | `/knowledge/quality` | 指標有無解釋？ |
| M8 | 管理 → 公司與帳號／部門權限 | `/governance/organization`、`/governance/departments` | 新增帳號、指派部門能否不看文件完成？ |

| M10 | 管理 → 問答品質 | `/governance/insights` | 圖表含義有無說明？ |
| M11 | 系統 → 功能開關 | `/system/modules` | 模組清單（五個職能模組）啟停是否直覺？「Seed Canonical Modules」這類工程用語是否該出現？（**已知風險點**） |

| J8 | 任務工作區（主路徑） | `/job/tasks/quote`、`/job/tasks/incident`、`/job/tasks/handover`、`/job/tasks/interview`、`/job/tasks/daily_report`、`/job/tasks/quality_8d`、`/job/tasks/training` | **主路徑**：語音／打字 → 欄位確認卡（來源標籤）→「送出審核」。檢查：入口是否從 `/job` 直接進來？欄位來源（語音／文字／手動）看得懂嗎？缺欄位黃框是否清楚？「檢視完整表單」會不會被誤當成唯一入口？ |

### 2.3 權限邊界測試（用 viewer 帳號＋直接輸入網址）

| # | 測試 | 預期 |
|---|------|------|
| P1 | viewer 直接輸入 `/governance/audit` | 被導回自己的首頁，**不得**看到內容或錯誤碼細節 |
| P2 | viewer 直接輸入 `/system/modules` | 同上 |
| P3 | employee 直接輸入 `/overview` | 導回 `/job` |
| P4 | 未登入訪問任何頁 | 導回 `/login` |
| P5 | 員工在文件頁嘗試上傳 | 無上傳入口（不是點了才 403） |
| P6 | 業務（sales 職能）登入 | 工作台**不應**出現 8D／交接班入口 |
| P7 | 隨意輸入不存在的網址 | 導回首頁，不出現白畫面或英文錯誤 |

### 2.4 選單檢查記錄

每個選單項記錄：**名稱看得懂（Y/N）／內容符合預期（Y/N）／空狀態有引導（Y/N/不適用）／問題描述＋等級**。

## 3. UIUX 通用體檢（每頁、每任務適用）

執行 §2 與各劇本任務時，觀察員同步用以下十個維度檢查：

| # | 維度 | 檢查問題 |
|---|------|----------|
| U1 | 狀態可見 | 系統正在做什麼（檢索中／轉寫中／送出中）有明確回饋嗎？等待超過 2 秒有無進度提示？ |
| U2 | 語言一致 | 全站是否混用中英文與工程術語（如 module_key、seed、instance）？按鈕是動詞開頭嗎？ |
| U3 | 可逆與容錯 | 誤觸能返回嗎？刪除／送出前有確認嗎？草稿會自動保存嗎？ |
| U4 | 錯誤可理解 | 錯誤訊息是人話（「網路不穩，請重試」）還是工程話（500／Exception）？有告訴使用者下一步嗎？ |
| U5 | 空狀態 | 無資料頁面是空白，還是有「為什麼是空的＋下一步可以做什麼」？ |
| U6 | 一致性 | 同類動作（送出／核准／匯出）在不同頁面的位置、顏色、用詞一致嗎？ |
| U7 | 來源可信 | 引用來源呈現是否一眼可辨？點得進去原文嗎？ |
| U8 | 手機適配 | 觸控目標夠大（≥44px）嗎？單手可操作嗎？表格在小螢幕可讀嗎？橫向捲動有提示嗎？ |
| U9 | 現場適配 | 字級在 1 公尺距離可讀嗎？噪音下語音狀態（聽不到／辨識中）可見嗎？手套可操作嗎？ |
| U10 | 認知負荷 | 一個畫面要使用者做的決定超過 3 個嗎？專有名詞有無即時解釋？ |

## 4. 劇本 A：業務／業務助理

**人物設定**：26–40 歲業務助理，每天回客戶詢價、查規格、做報價單；Excel 很熟，對 AI 系統陌生。
**測試裝置**：桌機瀏覽器為主；其中一輪改用手機 PWA。
**開場**：先做 §2.1 自由探索＋§2.2 員工選單檢查（E1–E3、J1–J7 中與報價相關項）。

### 任務 A1：第一次登入與工作台理解（5 分鐘）

**任務卡**：「你剛到職，登入系統後，請說說你覺得這個畫面可以做什麼，然後試著開始做一張報價單。」

| 項目 | 內容 |
|------|------|
| 操作路徑 | 登入 → 職能工作台（`/job`）→ 觀察是否出現「開報價單」等業務入口 |
| 預期結果 | 業務只看到 `sales_quote`、`spec_sop` 相關入口；不該看到品保 8D、交接班 |
| 觀察重點 | 不看教學能否找到報價入口？入口命名看得懂嗎？ |
| UIUX 檢查點 | U2（命名）、U5（無待辦時工作台是否空白無引導）、U10（入口是否過多） |
| 對應功能 | JobRole 指派、動態 workspace_entries、模組路由 |

### 任務 A2：查規格與版本差異（5 分鐘）

**任務卡**：「客戶問：P-200 的 v2.0 和 v2.1 規格差在哪？請找出答案並說明你為什麼相信這個答案。」

| 項目 | 內容 |
|------|------|
| 操作路徑 | 工作台 → 查規格／SOP（`/ask?module=spec_sop`）→ 提問 |
| 預期結果 | 引用 D01 三份規格書、列出 v2.0→v2.1 的 3 處差異、附來源 |
| 觀察重點 | 使用者會主動點來源確認嗎？回答缺來源時察覺嗎？ |
| UIUX 檢查點 | U1（檢索中回饋）、U7（來源呈現）、U2（「已切換至 XX 模組」這類系統訊息使用者看得懂嗎） |
| 對應功能 | 模組檢索範圍、版本比較 intent、引用呈現 |

### 任務 A3：任務工作區開報價單（10 分鐘，核心任務）

**任務卡**：「客戶『翔展科技』來電：要 P-200 三百 pcs，問什麼時候能交。請用**講的或打一行話**把這張報價單建起來。」

| 項目 | 內容 |
|------|------|
| 操作路徑 | 工作台 → 開報價單（`/job/tasks/quote`）→ 語音或文字輸入 → 欄位確認卡 → 補必填 →「送出審核」。完整表單（`/forms/quote`）僅當手動備援 |
| 預期結果 | 辨識出客戶名、品號、數量、單價；來源標「語音／文字」；缺欄位黃框；可送審。文字備案句：「幫翔展科技報價，料號 P-200，三百個，單價一千一百五十」 |
| 觀察重點 | 使用者第一反應是講／打字還是找空白表單？辨識錯誤時知道怎麼改嗎？會不會以為一定要進完整表單？ |
| UIUX 檢查點 | U1（轉寫／抽取中狀態）、U3（欄位卡改錯字）、U4（辨識失敗提示）、U8（語音按鈕）、U10（欄位卡 vs 完整表單認知負荷） |
| 對應功能 | TaskEngine quote run；`/tasks/runs/{id}/parse-text`；voice transcribe；execute → form + approval |
| 已知邊界 | STT 僅 OpenAI；regex 抽取先顧 customer／part_number／quantity／unit_price／date；付款條件等需手動補 |

### 任務 A4：套用公司版型預覽與送審（5 分鐘）

**任務卡**：「把剛才的報價單用公司格式看一下，沒問題就送給主管簽。」

| 項目 | 內容 |
|------|------|
| 操作路徑 | 表單頁 → 版型預覽（T01）→ 送審 |
| 預期結果 | 預覽呈現公司 DOCX 版型且欄位映射正確；送審產生待審核請求 |
| 觀察重點 | 預覽與心中的「公司格式」一致嗎？欄位錯位會被發現嗎？ |
| UIUX 檢查點 | U3（送審前有確認嗎）、U6（「送審」按鈕位置與其他表單一致嗎）、U4（版型渲染失敗時的訊息） |
| 對應功能 | FormTemplate 上傳／映射／啟用／預覽；submit 產生 ApprovalRequest |

### 任務 A5：主管核准與正式匯出（5 分鐘，換主管帳號）

**任務卡**（給主管）：「有一張報價單等你簽，請看完內容後核准，然後把正式檔案存下來。」

| 項目 | 內容 |
|------|------|
| 操作路徑 | 主管登入 → 審核收件匣（`/approvals`）→ 檢視快照 → 核准 → 回業務帳號 → `/forms/mine` → 詳情 → 匯出 DOCX |
| 預期結果 | 狀態流轉正確；匯出檔使用不可變快照與公司版型；匯出歷程有記錄 |
| 觀察重點 | 主管看得懂在簽什麼嗎？業務找得到「我的表單」和匯出按鈕嗎？ |
| UIUX 檢查點 | U5（收件匣空的狀態）、U6（核准／退回／要求修改三按鈕區分）、U2（「不可變快照」等術語是否該出現在 UI） |

## 5. 劇本 B：設備與現場人員

**人物設定**：30–55 歲現場作業員／設備技術員，可能戴手套、環境有噪音、不習慣打長字。
**測試裝置**：手機 PWA（主場）；其中一輪在**播放白噪音**環境執行語音任務。
**開場**：§2.1 自由探索（手機上進行）＋員工選單檢查 E1–E3。

### 任務 B1：掃碼進入設備場景（5 分鐘）

**任務卡**：「你走到 EQ-100 前面，用系統開始查這台機器的東西。」

|------|------|

| UIUX 檢查點 | U1（相機啟動與解析中回饋）、U4（掃不到的提示）、U8／U9（單手、手套、1 公尺字級） |

### 任務 B2：場景限定問答與安全指引（5 分鐘）

| 操作路徑 | 場景內直接語音或打字提問「E-07 怎麼處理」 |

## 6. 劇本 C：資深師傅／訓練負責人

**人物設定**：50 歲以上資深師傅（知識提供者）＋兼任訓練負責人的主管（知識治理者），可分兩人執行。
**測試裝置**：桌機為主。
**開場**：§2.1 自由探索＋員工選單檢查（師傅視角）＋主管選單檢查 M1–M14（主管視角，重點 M6 兩處「審核」混淆、M11 功能開關用語）。

### 任務 C1：訪談建卡（15 分鐘，核心任務）

**任務卡**（給師傅）：「請把你處理『機台張力異常』的經驗留下來，讓新人以後查得到。系統會問你幾個問題，你用講的或打的回答。」

| 項目 | 內容 |
|------|------|
| 操作路徑 | 工作台 → 訪談建卡（`/job/tasks/interview`；備援 `/knowhow/interview`）→ 同意記錄聲明 → 口述或貼上逐字稿 → 系統抽取步驟／風險／注意事項 → 產生知識卡草稿 |
| 預期結果 | 草稿含結構化步驟、適用設備、注意事項；師傅看得到系統「聽懂了什麼」 |
| 觀察重點 | 師傅講故事、系統抽步驟——抽錯的地方會改嗎？consent 聲明會造成疑慮嗎？ |
| UIUX 檢查點 | U2（「抽取」「逐字稿」等詞師傅懂嗎）、U3（抽取結果可編輯嗎）、U10（一次呈現的欄位是否過多） |
| 對應功能 | interview extract、知識卡草稿、lineage 記錄 |
| 測試素材 | 3–5 分鐘真實口述（可預錄），刻意包含：正規步驟＋一個「老師傅眉角」＋一個與 D02 SOP 矛盾的舊做法（配合 D10） |

### 任務 C2：SOP 衝突處置（10 分鐘）

**任務卡**：「系統說你剛才的經驗跟正式 SOP 有地方對不起來，請你看看是怎麼回事，然後決定怎麼辦。」

| 項目 | 內容 |
|------|------|
| 操作路徑 | 知識卡草稿 → 衝突提示 → 檢視差異（師傅做法 vs D02 SOP）→ 標記處置 → 再送審 |
| 預期結果 | 未解決衝突**擋住送審**；解決後才可送出；衝突報告留存 |
| 觀察重點 | 師傅看得懂「衝突」嗎？會不會覺得系統在否定他的經驗（文案觀察）？ |
| UIUX 檢查點 | U4（衝突說明是人話嗎）、U7（並排顯示 SOP 原文嗎）、U6（「解決」的動作明確嗎） |
| 對應功能 | SOP 衝突檢查（真 Document 查詢）、conflict_report、submit 阻擋 |

### 任務 C3：審核與發布（5 分鐘，主管視角）

**任務卡**（給主管）：「有一張知識卡等你審，請決定要不要讓它變成新人可以查的正式知識。」

| 項目 | 內容 |
|------|------|
| 操作路徑 | `/approvals` → 檢視知識卡與衝突處置紀錄 → 核准 |
| 預期結果 | 核准後卡片 `approved`、可被檢索；系統建立 180 天複核提醒 |
| 觀察重點 | 主管核准前有足夠資訊嗎（來源、訪談 lineage、衝突紀錄）？ |
| UIUX 檢查點 | U5（待審清單資訊量）、U2（「lineage」「生命週期」等詞不該出現在 UI） |
| 對應功能 | decide_approval、MKAReviewReminder |

### 任務 C4：新人查得到嗎（5 分鐘，新人視角）

**任務卡**（換新人帳號）：「你是新人，機台張力好像不太對，查查看公司有沒有相關的處理經驗。」

| 項目 | 內容 |
|------|------|
| 操作路徑 | 新人帳號 → 工作台（應以 training_knowhow 為主）→ 提問或查訓練清單 |
| 預期結果 | 查到 C1–C3 核准的知識卡；**草稿或未核准的卡不出現**；同場完成 `training_checklist` |
| 觀察重點 | 知識卡呈現（步驟／注意事項／來源）新人看得懂嗎？ |
| UIUX 檢查點 | U5（新人工作台無待辦時的引導）、U10（訓練清單長度） |
| 對應功能 | 知識卡狀態隔離、新人職能工作台、training_checklist 表單 |

### 劇本 C 特別觀察題

- 師傅願不願意「被記錄」？consent 與音訊保留政策說明夠透明嗎？
- 訪談到上線的**總耗時**——超過耐心阈值就是流程要簡化的訊號。
- 主管在 `/approvals` 與 `/knowledge/review` 之間會混淆嗎？

## 10. 已知邊界（測試與 DEMO 前必讀）

| 邊界 | 影響 | 應對 |
|------|------|------|
| 開單主路徑已改為 Task Workspace | 舊習慣「直接開 `/forms/...` 填」會覺得產品半套 | 測試與 Demo 一律從 `/job/tasks/...` 進；表單標成備援 |

| regex 欄位抽取覆蓋有限 | 付款條件／複雜交期等需手動補 | Demo 台詞預告「關鍵欄位它抽，其餘你確認」 |

| 盲測答題率約 78–79% | 問答可能答錯或過拒 | Demo 題目從已驗證語料出；現場提問環節要有人護航 |

| 兩處「審核」入口（`/approvals` vs `/knowledge/review`） | 使用者可能混淆 | 列入 §2.2 M6 重點觀察；測後決定是否改名或合併 |
| 部署後舊前端 shell 快取 | 深連結新路由可能被彈回 `/job` | 已修 nginx／SW `no-cache`；Demo 前硬重新整理一次 |
