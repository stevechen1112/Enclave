# ADR-003：單客戶地端部署與未來 SaaS 相容邊界

**狀態**：已接受
**日期**：2026-07-31
**決策者**：Enclave 技術團隊

---

## 背景

Enclave 首發販售模式為每客戶一套地端部署（Single-Customer On-Premise）。但未來可能擴展為多租戶 SaaS。需要在架構上預留相容性，避免日後大規模重構。

## 決策

**第一版以單租戶地端為設計目標，但資料模型與 API 保留多租戶相容性。**

### 具體措施

1. **資料模型**：所有核心表保留 `tenant_id` 欄位（即使初期只有一個租戶）。不對單租戶做 schema 簡化。
2. **API**：所有端點接受 `tenant_id` 參數（從 JWT 提取），不對單租戶做省略。
3. **部署**：第一版 Docker Compose 為單節點部署。不引入 Kubernetes 或 multi-master DB。
4. **隔離**：初期使用 PostgreSQL schema 級隔離（`tenant_id` WHERE 子句）。不引入實體資料庫隔離。
5. **授權**：授權模組支援 `tenant_id` 維度，即使初期只有一個租戶。

### 明確不做事項

- 不預先實作多租戶 SaaS 的計費、試用、自助註冊。
- 不引入跨租戶的資源池或共享向量庫。
- 不為 SaaS 做多區域部署。

## 理由

1. **避免日後重構**：`tenant_id` 欄位在初期幾乎零成本，但日後加入的成本極高。
2. **客戶接受度**：地端客戶通常要求單一部署實體，但資料模型的多租戶設計不影響他們。
3. **漸進式演進**：若日後推出 SaaS 版，核心資料模型無需變更。

## 後果

- 所有 SQL 查詢需帶 `tenant_id` 過濾（即使只有一個租戶）。
- 測試需涵蓋多租戶場景（即使初期不部署多租戶）。
