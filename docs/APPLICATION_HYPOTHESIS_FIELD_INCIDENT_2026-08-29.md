# 候選應用假設：現場異常事件處理

**日期：** 2026-08-29  
**狀態：** 待驗證的應用假設；不是既定 Roadmap、第一優先或已核准開發項目  
**所屬：** MKA Domain Pack；使用核心 Input、問知識、Evidence、Workflow 與租戶權限  
**目的：** 保存目前對異常回報、處理與交接的分析素材，供應用層零基審查使用；不得因已有此文件或既有程式就推定本應用應被產品化。

---

## 1. 這個應用是誰

### 正式名稱

**現場異常事件處理**

使用者介面可簡稱：**異常事件**。

### 一句話定義

讓現場人員能用最短時間把異常安全地回報，讓適當的人接手處理，讓每次判斷與處置都有來源、狀態與責任，直到確認解決、完成交接並沉澱成可搜尋案例。

### 它不是什麼

- 不是只有一張「異常回報表」。
- 不是完整 CMMS、MES 或 EAM 的替代品。
- 不會依照片、聲音或 AI 推論直接判定根因。
- 不會取代正式緊急應變程序、合格維修人員或主管決策。
- 不會在沒有正式證據時提供高風險拆卸、旁路或帶電操作步驟。
- 第一階段不直接控制機台，也不自動寫回 ERP／MES。

### 場景完成的真正定義

不是「表單已送出」，而是：

```text
異常已被看見
＋ 已有人負責
＋ 安全風險已處理
＋ 處置與證據已記錄
＋ 未完成事項已正確交接
＋ 結果已確認並可追溯
```

## 2. 使用者不綁公司職稱，只定義事件責任

本場景不在產品中寫死「作業員、班長、設備、品保」等角色。不同租戶可以用不同職稱，只需把人員放進三種事件責任：

| 事件責任 | 能做什麼 | 公司可能對應的人員 |
|---|---|---|
| 回報人 | 建立異常、補充現象、附件與已採取措施 | 任何被允許使用本應用的人。 |
| 處理人 | 接手、更新處置、建立待辦、標記已解決 | 維修、工程、品保、現場主管或其他租戶指定人員。 |
| 確認／結案人 | 確認風險解除、結果有效並關閉事件 | 主管、設備負責人、品保或租戶指定人員。 |

同一個人可以同時是回報人與處理人；低風險事件也可以由同一人完成。高風險事件是否要求另一人確認，由場景政策決定。

### 租戶標準設定只保留五項

1. 是否啟用「異常事件」。
2. 開放全公司、指定部門或指定人員使用。
3. 預設處理人或處理群組。
4. 緊急事件聯絡人與聯絡方式。
5. 哪些嚴重度必須由另一人確認後才能結案。

進階權限、能力 key、ACL 與狀態轉換保留在系統底層，不要求一般租戶自行組合。

## 3. 誰在什麼時候進入

### 回報人進入

- 發現機台、品質、安全、物料或生產異常時。
- 掃描設備／工單 QR 後點擊「回報異常」。
- 在問知識或其他工作中判斷需要建立正式事件時。
- 從手機首頁以語音、拍照或快捷按鈕直接開始。

### 處理人進入

- 收到新事件指派或緊急升級。
- 查看自己的待處理、逾期或跨班未完成事件。
- 需要查適用 SOP、歷史案例或補充處置證據時。

### 確認／結案人進入

- 事件被標記為已解決，等待確認時。
- 高風險事件需要核對正式依據與處置結果時。
- 重複發生、需要轉成品質改善或知識修訂時。

## 4. 十項場景問題：現況、建議與租戶設定

| 檢視問題 | 現有設定／能力 | 建議預設 | 租戶導入時要確認 |
|---|---|---|---|

| 2. 要完成什麼工作？ | 目前主要完成異常表單並送審。 | 建立事件、確保安全、指派、處置、交接、確認與結案。 | 哪些事件需跨部門、何時算解決、誰能結案。 |

| 9. 手機、平板、桌機是否適用？ | 現有工作台與表單是響應式、大按鈕、語音與 QR；尚未完成現場附件及弱網驗證。 | 手機優先回報；平板處理與查證；桌機做長篇分析、管理及報表。支援中斷續填與失敗重試。 | 廠內網路、裝置、噪音、手套、相機／麥克風政策。 |
| 10. 成效如何量測？ | 模組宣告 `incident_time`、`safety_acks`；通用 Task metrics 有完成、失敗、來源及簽核時間。 | 量測回報、接手、解決、結案時間，遺漏率、重複率、交接遺漏、安全確認及人工修改率。 | 目前基準、SLA、抽樣驗證方式與試行目標。 |

## 5. 建議的標準使用者旅程

```text
發現異常
  → 若疑似緊急，先顯示正式緊急程序與聯絡方式
  → 掃 QR／語音描述／拍照／手動輸入
  → 自動帶入人員、時間、廠區、產線、設備與工單
  → 只確認最小回報資料
  → 立即建立事件並通知預設處理人
  → 系統提出分類、嚴重度、適用 SOP 與歷史案例候選
  → 人員確認風險與是否停機／升級
  → 處理人記錄檢查、處置、零件、附件與待辦
  → 未完成事件自動進入交接
  → 處理人標記已解決
  → 必要時由另一人確認並結案
  → 產生結案摘要、日報素材與知識候選
```

### 緊急狀況優先

遇到火災、爆炸、漏電、受傷、冒煙、化學洩漏等訊號時，不應先要求填完整表單。第一畫面應先提供：

- 確保人員安全。
- 依正式緊急程序停機、撤離或隔離。
- 顯示租戶設定的緊急聯絡人。
- 明確告知 AI 不取代合格安全與維修人員。

完成必要安全動作後再補建事件資料。

## 6. 建議事件資料結構

### 最小建立資料

- 發生了什麼：語音、文字或附件至少一項。
- 發生位置：設備、產線、區域或其他可辨識位置至少一項；緊急時允許稍後補充。
- 是否疑似有人身或重大安全風險。
- 發生／發現時間：預設現在，可修改。
- 回報人：登入者自動帶入。

### 後續處理資料

- 事件類別與嚴重度。
- 設備、產品、料號、工單及班次。
- 症狀與觀察。
- 已採取的立即措施。
- 處理人與期限。
- 檢查紀錄、處置與更換零件。
- 根因候選與最終確認。
- 相關 SOP、歷史案例與 Evidence。
- 照片、音訊、影片及其他附件。
- 解決結果、驗證方法及結案人。
- 是否需要轉成 8D／CAPA 或知識修訂。

### 欄位來源

每項資料保留：

- 來源類型：使用者、語音、scene、QR、照片分析、知識、外部系統或規則。
- 原始參照與時間。
- 信心或解析狀態。
- 誰確認或修改。
- 正式文件版本與 Evidence locator。

## 7. 狀態與責任

建議使用五個一般使用者能理解的狀態：

```text
草稿
→ 已回報
→ 處理中
→ 待確認
→ 已結案
```

另有兩個跨狀態標記：

- **已升級**：需要緊急、主管、品保或其他租戶指定介入。
- **已取消**：誤報或重複事件，必須保存原因與稽核紀錄。

交接班不是另建一份不相干資料，而是將仍在「已回報／處理中／待確認」的事件指派給下一班並留下接手確認。

工作日報也不重填事件，而是依日期、班次與人員自動彙整事件時間軸，再讓使用者補充其他工作。

## 8. AI、Evidence 與人類決策邊界

### AI 可以做

- 從語音或文字擷取設備、現象、時間及已採取措施。
- 建議事件類別及嚴重度。
- 從照片、聲音或影片產生候選描述。
- 找出適用 SOP、規格與相似歷史案例。
- 摘要事件時間軸。
- 建議還缺哪些資料。
- 產生交接與結案摘要草稿。

### AI 不可自行決定

- 人員是否安全。
- 是否解除安全裝置。
- 是否進行帶電、高壓、高溫或化學操作。
- 最終停機／復歸決定。
- 最終根因。
- 品質放行。
- 事件是否可正式結案。

### Evidence 規則

- 高風險操作建議必須引用適用且有效的正式 SOP。
- 相似案例只能標示為參考，不等於正式程序。
- 圖片、音訊及影片分析是候選，不等於已確認事實。
- 使用者必須能從事件中的指引、判斷或處置打開原始來源。
- 找不到合格證據時，系統應停止提供高風險操作步驟並要求合格人員介入。

## 9. 通知與確認原則

### 回報不需要等待核准

異常回報的目的，是讓事件立即被看見。如果先要求 owner／admin 核准，可能延誤處置。因此建議：

- 事件建立後立即成為「已回報」。
- 高風險事件立即通知，不等待核准。
- 缺少非安全關鍵資料可稍後補齊。

### 結案才依風險確認

- 低風險：可允許處理人自行結案，或由租戶選擇是否確認。
- 中風險：建議由另一位確認人結案。
- 高風險：必須由租戶指定的確認人核對處置、證據與風險解除。

### 通知最小需求

- 新事件指派。
- 高風險升級。
- 即將逾期與逾期。
- 處理人變更。
- 等待結案確認。
- 跨班仍未完成。

通知通路第一版以產品內待辦為主；Email、LINE、Teams、簡訊或其他外部通路依租戶需求逐步接入。

## 10. 建議成效指標

| 指標 | 定義 |
|---|---|
| 回報時間 | 從開始輸入到事件成功建立。 |
| 接手時間 | 從事件建立到第一位處理人確認接手。 |

| 人工修改率 | AI／語音帶入欄位被人工修正的比例。 |

## 11. 現有設定保留與調整建議

### 建議保留

- `incident_handover` 作為模組邊界。
- `require_equipment` 的知識範圍概念，但緊急回報不可因沒有 equipment ID 被阻擋。
- `safety_first_prompt=true`。
- `severity` 與 `equipment_id` 為高風險欄位的概念。
- `incident` TaskDefinition 為 high risk。
- TaskRun、field source、provenance、scene context、approval、immutable snapshot 與 audit 能力。
- 現有異常、維修、交接及日報表單欄位作為資料字典與輸出基礎。
- `SafeGuidancePolicy`、SceneAdapter、IncidentStatus、TaskAssignment 與 ShiftHandover 原型中的安全及事件概念。

### 建議調整

1. `require_scene_for_incident=false` 保留為回報預設，但沒有 scene 時在事件建立後提示補充，不阻止緊急回報。
2. 移除異常回報一律 `require_approval=true` 的產品流程；改為立即回報、依風險確認結案。
3. 將設備維修、交接班與日報從獨立入口改成事件的後續動作或自動彙整結果。
4. 將通用 `FormInstance` 升級為真正 Incident aggregate，表單只作為輸入／匯出 view。
5. 將 scene 從工作台完整傳入 TaskRun；目前 Task Workspace 沒有接住導航 state。
6. 將照片、短影片、音訊及附件整合到事件，而不是只存在原型欄位。
7. 將安全 policy 接入正式建立與更新流程；不能只存在獨立 service 與單元測試。
8. 將處理人、期限、事件時間軸、交接確認、通知與結案驗證做成正式持久化能力。
9. 租戶設定改為簡單的開放範圍、預設處理人、緊急聯絡人及結案規則，不要求自訂 capability 組合。

## 13. 場景完成驗收條件

1. 任一被授權人都能在手機上以最小資料快速建立事件。
2. 緊急關鍵字會先顯示正式安全程序與租戶聯絡方式，不會先要求填完整表單。
3. QR／scene 能正確帶入廠區、產線、設備或工單並保存於事件。
4. 文字、語音、照片、音訊或短影片至少能以受治理附件形式進入事件。
5. AI 建議的分類與嚴重度清楚標示，且由人確認。
6. 高風險指引沒有有效正式 Evidence 時 fail closed。
7. 事件有回報人、處理人、狀態、期限、時間軸與結案紀錄。
8. 未完成事件能跨班交接並由接班人確認。
9. 日報能引用事件資料，不要求重複輸入。
10. 租戶只需完成五項簡單設定，不必自行建立 capability 組合。
11. 租戶、部門、事件與附件權限不會跨界洩漏。
12. 桌機、平板、手機、弱網、中斷續填、相機／麥克風拒絕及失敗重試均完成驗收。
13. P0／P1 實作分階段完成 code review 後，才可進入下一階段。
