# 製造業知識助理：產品願景、功能架構與落地計畫

**文件版本**：1.0  
**日期**：2026-08-05  
**產品底座**：Enclave  
**文件定位**：產品構想、使用者體驗、技術可行性與階段性落地規格  
**核心產業**：製造業，優先服務外銷企業

---

## 1. 執行摘要

目前 Enclave 的核心能力是「企業知識庫＋文字問答」：公司將合約、規格、SOP、表單、手冊等文件入庫，使用者可以依權限檢索、提問、取得來源引用，系統在證據不足時拒答。

下一階段不應只是替聊天頁面增加更多按鈕，而應將 Enclave 擴充成：

> **以職務為入口、語音為主要互動方式、企業知識為底座、工作模組負責產出的製造業知識作業平台。**

產品從「回答問題」提升為「協助完成工作」：

```text
語音／文字提出需求
→ 辨識職務與工作場景
→ 取得有權限的企業知識
→ 補問缺少欄位
→ 執行規則化計算或工具
→ 套用公司 Fixed Form
→ 人工確認／主管審核
→ 產生正式文件或送入下一流程
```

技術上可行，而且 Enclave 已具備大部分底層骨架；但完整產品仍需補上行動端、語音管線、職能模組框架、動態表單、規則計算、審核流程及外部系統串接。

現階段最適合的產品承諾是「有來源、可控、需人確認的工作助理」，不應承諾完全自主決策或未經確認直接執行正式交易。

## 2. 問題與市場背景

### 2.1 製造業知識散落

製造業的重要知識通常散落於：

- SOP、設備手冊、產品規格與檢驗標準
- 報價單、合約、訂單、請款與客戶往來
- 研發文件、測試紀錄、配方與版本差異
- 維修紀錄、異常報告與客訴處理
- 資深人員腦中的經驗、眉角與判斷方式
- LINE、Email、錄音、會議及紙本表單

問題不是完全沒有資料，而是資料分散、版本不明、權限不清，也無法在工作當下快速取得。

### 2.2 現場人員不一定擅長打字

製造現場與傳統產業使用者常見限制：

- 不習慣輸入長文字
- 工作中戴手套或手部忙碌
- 料號、設備代碼與專有名詞難輸入
- 不知道該用什麼關鍵字搜尋
- 不想打開複雜後台或逐層找資料夾

因此行動裝置與語音很適合作為入口，但語音必須搭配文字確認、選單、掃碼與人工審核，不能成為唯一操作方式。

### 2.3 企業真正需要的不是聊天

單純問答可以解決「我想知道什麼」，但企業日常更常出現：

- 幫客戶做一份報價
- 整理一份設備異常紀錄
- 產生請款單或會議紀錄
- 找出適用的 SOP 並形成檢查表
- 比較產品規格與交期
- 把老師傅口述轉成可審核的知識

產品價值必須從「找到答案」走向「以答案完成工作」。

## 3. 產品定位

### 3.1 建議定位

不建議只稱為「AI 知識庫」，因為客戶往往不知道知識庫具體能帶來什麼結果。

建議定位為：

> **製造業知識作業平台：將散落的文件與人員經驗，轉化為可查詢、可生成、可執行、可審核、可傳承的工作能力。**

另一個較口語的說法：

> **企業記憶＋每個職務的 AI 工作助理。**

### 3.2 核心與垂直層分離

產品架構應分成兩層：

**通用核心 Enclave**

- 文件入庫、OCR、解析與索引
- 多租戶、部門及文件權限
- 檢索、問答、來源引用與拒答
- 生成、稽核、紀錄與可觀測性
- API、身分驗證、配額與安全控制

**製造業解決方案層**

- 職能模組
- 製造業文件分類
- 固定表單
- 產業規則與計算工具
- 審核流程
- ERP、CRM、MES 等連接器
- 行動與語音使用體驗

這樣可以維持核心技術的普遍性，同時讓商業產品高度聚焦製造業。

## 4. 產品設計原則

### 4.1 Voice-first，不是 Voice-only

語音是主要入口，但重要欄位仍需顯示與確認：

- 金額
- 數量
- 料號
- 客戶名稱
- 日期與交期
- 設備代碼
- 報價版本

任何正式輸出前，都應讓使用者看到結構化摘要並確認。

### 4.2 以工作場景為模組，不只是以部門分類

「業務部」只是權限範圍；「建立報價單」才是使用者真正要完成的工作。

模組應以可完成的任務命名，例如：

- 查詢產品規格
- 建立報價草稿
- 記錄設備異常
- 產生交接紀錄
- 建立 8D 報告
- 新人崗位學習

### 4.3 正式知識與經驗知識必須分級

知識權威建議由高到低分為：

1. 已核准制度、SOP、合約與正式規格
2. 已審核的作業指引與案例
3. 已審核的資深人員 know-how
4. 尚未審核的訪談或語音轉寫草稿
5. 外部參考資料

回答若同時遇到正式 SOP 與老師傅口述衝突，必須以正式版本優先，並主動顯示差異。

### 4.4 LLM 負責理解，程式負責確定性

AI 適合：

- 理解口語需求
- 找資料
- 摘要與起草
- 辨識缺少欄位
- 將內容整理成結構

程式規則應負責：

- 價格與折扣計算
- 稅額與幣別換算
- MOQ 與交期規則
- 欄位驗證
- 權限檢查
- 核准與正式送出

正式金額不可只靠 LLM 心算或自由生成。

### 4.5 預設人機協作

初期所有具法律、財務或生產風險的輸出都應採：

```text
AI 草稿 → 使用者確認 → 主管／指定角色核准 → 正式輸出
```

未來可以依風險逐步開放自動化，但不應第一天就追求無人化。

## 5. 行動 APP 與語音體驗

### 5.1 首頁依職務顯示

使用者登入後，系統依 tenant、role、department 與授權模組顯示功能。

例如業務首頁：

- 問產品
- 查規格
- 建立報價
- 比較版本
- 建立請款草稿
- 查詢最近客戶紀錄

例如設備人員首頁：

- 掃描設備
- 問操作方式
- 回報異常
- 查保養週期
- 建立維修紀錄
- 查歷史案例

### 5.2 建議互動元件

- 按住說話
- 語音即時轉文字
- 文字修正與重新錄音
- 快速選項與確認按鈕
- 相機拍照
- QR Code／條碼掃描
- 來源文件卡片
- Fixed Form 預覽
- 審核狀態與通知

### 5.3 製造現場特別適合「場景先行」

與其讓使用者說完整背景，不如先透過掃碼或畫面建立範圍：

```text
掃設備 QR Code
→ 系統知道工廠、產線、設備型號與版本
→ 使用者語音詢問「現在出現 E27，要先檢查什麼？」
→ 只搜尋該設備的正式手冊、SOP 與已審核案例
```

其他例子：

- 掃工單後詢問交期或下一站
- 掃產品條碼後查規格與包裝方式
- 拍瑕疵品後口述問題並建立異常草稿
- 進入特定客戶頁面後說「沿用上次折扣報五百件」

場景資訊可以大幅降低語音歧義與檢索錯檔。

### 5.4 語音的現實限制

必須考慮：

- 工廠噪音
- 台語、口音與中英混用
- 料號、縮寫與客戶名稱
- 網路不穩定
- 多人同時說話
- 機密資訊被旁人聽見

必要措施：

- 公司專有詞與料號字典
- 關鍵欄位二次確認
- 耳機與按住說話模式
- 可切換文字、選單與掃碼
- 錄音保存政策與權限
- 高風險內容不直接以 TTS 大聲播放

### 5.5 APP 實作策略

建議先做手機友善 PWA 或既有 Web 的行動殼，驗證工作流程，再決定是否投入完整原生 APP。

PWA 適合第一階段：

- 開發快
- 共用 Enclave API
- 可支援麥克風、相機與基本掃碼
- 更新不需經過 App Store

需要原生 APP 的條件：

- 離線工作
- 背景錄音或大量音訊處理
- 推播與深度連結
- 藍牙設備、NFC 或特殊掃碼器
- 更嚴格的裝置管理

## 6. 職能模組架構

### 6.1 模組不是 Prompt

真正的職能模組至少應定義：

- 模組名稱與適用角色
- 可以存取的知識範圍
- 支援的使用者意圖
- 可呼叫的工具與計算器
- 可產出的表單
- 必填欄位與驗證規則
- 審核角色
- 是否允許正式送出
- 稽核紀錄
- 版本與啟用狀態
- 成效指標

若只是換 system prompt，不足以形成可控的企業產品。

### 6.2 建議第一批模組

#### 模組 A：規格與 SOP 助理

適用：業務、生產、設備、品質、新人。

能力：

- 依產品、設備與版本查詢
- 顯示來源、頁面與生效版本
- 比較兩版 SOP 或規格差異
- 證據不足時拒答
- 將步驟轉成現場 checklist

這是風險最低、最接近 Enclave 現有能力的第一個模組。

#### 模組 B：業務報價助理

適用：業務、業務主管、財務。

能力：

- 語音輸入客戶、產品、數量與條件
- 查產品規格、歷史報價與價格政策
- 透過規則引擎計算
- 追問缺少欄位
- 產生公司格式報價草稿
- 送主管審核
- 核准後匯出 PDF／Word

這是 ROI 高、但需要嚴格計算與審核的模組。

#### 模組 C：現場異常與交接

適用：生產、設備、品管、班組長。

能力：

- 掃設備或工單
- 語音描述異常
- 查 SOP 與歷史案例
- 建議檢查順序，不代替安全判斷
- 形成異常／交接紀錄草稿
- 指派待辦與追蹤狀態

這是最能體現手機與語音價值的模組。

#### 模組 D：品質與客訴

適用：品保、業務、研發。

能力：

- 匯整客訴附件與歷史案例
- 對照檢驗規格
- 建立 8D／CAPA 草稿
- 追蹤責任人與期限
- 引用正式證據

#### 模組 E：職務訓練與知識傳承

適用：新人、主管、資深人員。

能力：

- 依職務建立必讀內容
- 情境問答與測驗
- 語音訪談與轉寫
- 產生待審核知識卡
- 記錄完成度與常見錯誤

## 7. Fixed Form 文件產出

### 7.1 為何不能只自由生成

企業文件通常有固定欄位、格式與責任，因此不能只要求 AI「幫我寫一份報價單」。

Fixed Form 應包含：

- 表單版本
- 欄位型別
- 必填與選填
- 預設值
- 資料來源
- 計算公式
- 驗證規則
- 權限
- 審核流程
- Word／PDF／Excel 版型

### 7.2 建議資料流程

```text
自然語言需求
→ Intent 與欄位抽取
→ 顯示已辨識欄位
→ 查公司知識與業務系統
→ 補問缺少欄位
→ 規則計算
→ 產生結構化 JSON
→ 套版
→ 預覽
→ 審核
→ 正式輸出
```

### 7.3 第一批 Fixed Form

建議優先順序：

1. 報價單草稿
2. 會議／拜訪紀錄
3. 異常與交接紀錄
4. 設備維修紀錄
5. 請款單草稿
6. 8D／CAPA 草稿
7. 新人訓練 checklist

合約可生成草稿，但應晚於一般表單，且必須有法務或授權人員審核。

## 8. 語音 Know-how 與知識傳承

### 8.1 收集流程

```text
訪談／現場口述
→ 語音轉寫
→ 分段與主題辨識
→ 提取步驟、條件、風險與例外
→ 對照現有 SOP
→ 產生知識卡草稿
→ 資深人員／主管審核
→ 發布為已核准經驗知識
```

### 8.2 不可直接自動發布

口述內容可能：

- 記錯
- 已過時
- 與正式 SOP 衝突
- 只適用特定設備或客戶
- 包含個資或機密
- 是習慣做法而不是合規做法

所以語音轉寫必須先進入「草稿區」，不能直接成為正式答案來源。

### 8.3 知識卡建議欄位

- 標題
- 適用職務
- 適用設備／產品／客戶
- 問題情境
- 建議處理方式
- 前置條件
- 風險與禁止事項
- 來源錄音與轉寫
- 訪談者、受訪者
- 審核者
- 生效日期與版本
- 關聯 SOP

## 9. Enclave 現況與支撐能力

### 9.1 已具備的底座

目前 Enclave 已具備：

- 多租戶與使用者身分
- role、department 與文件權限
- 文件上傳、OCR、解析與 chunks
- RetrievalFacade 與 MultiStepOrchestrator
- Catalog／Chunk／Compiled 多粒度檢索
- 串流聊天、多輪對話與來源
- 拒答與 source verifier
- 生成端點與既有模板
- 報告保存與 PDF 匯出
- SSO、MFA、配額、稽核與可觀測性

可直接支援的近期產品：

- 手機版文字／語音問答
- 依部門與職務限制知識
- 根據指定文件產生草稿
- 提供來源與拒答
- 人工確認後輸出文件

### 9.2 現有生成能力

Enclave 已有生成 API，支援：

- 生成模板
- 使用者指令
- RAG 查詢
- 指定文件 ID
- 串流輸出
- 來源與匯出

既有模板偏向函件、案件摘要、會議紀錄、分析報告及 FAQ，能作為 Fixed Form 的前身，但目前主要仍是 Markdown 生成模板，不等於完整的企業表單引擎。

### 9.3 尚缺的產品層

尚需建置：

- STT／TTS 與音訊 API
- 行動端／PWA／原生 APP
- 公司專有詞與料號字典
- 職能模組註冊與授權框架
- JSON Schema 動態表單
- 確定性計算與規則引擎
- 審核、簽核與狀態機
- 公司 Word／PDF／Excel 套版
- QR／條碼與場景上下文
- ERP／CRM／MES／庫存等連接器
- Know-how 審核與知識生命週期

### 9.4 能力邊界

Blind Z3 與 Z4 對未見文件的一次評測約 78–79%。後續已修復若干產品洞，但正式基線分數維持凍結。

因此 Enclave 目前適合：

- 協助查詢
- 協助起草
- 提供來源
- 引導填表
- 人工確認後使用

目前不適合承諾：

- 任意文件、任意問題皆正確
- 自動核價
- 無人審核簽發合約或報價
- 無人監督修改 ERP／MES
- 語音永遠精準理解

結論：

> **Enclave 撐得起這個產品方向，但目前撐的是可靠底座，不是完整成品。**

## 11. 階段性落地路線

### Phase 0：產品底座確認

目標：

- 穩定現有問答
- 保持來源與拒答
- 確認部門／角色權限
- 建立模組資料契約

完成判準：

- 模組不是硬編 Prompt
- 每次檢索均帶 AuthorizationContext
- 正式輸出可追溯來源與使用者

### Phase 1：手機友善＋語音輸入

範圍：

- PWA
- 按住說話
- STT
- 轉寫確認
- 語音專有詞字典
- 查規格／SOP

完成判準：

- 使用者可不打長文字完成問答
- 金額、料號、設備代碼必須確認
- 語音錯誤不會直接觸發正式操作

### Phase 2：第一個工作模組＋Fixed Form

建議先做：

- 業務報價草稿，或
- 現場異常／交接紀錄

完成判準：

- 可從自然語言抽欄位
- 缺欄位會追問
- 公式由程式計算
- 可套公司格式
- 有預覽與人工確認

### Phase 3：職能模組平台

範圍：

- 模組註冊
- 角色與部門啟用
- 模組工具權限
- 表單版本
- 審核流程
- 模組使用指標

完成判準：

- 新增模組不需修改核心問答
- 不同公司可啟用不同模組與版型

### Phase 4：Know-how 與訓練

範圍：

- 訪談錄音
- 轉寫
- 知識卡
- SOP 差異偵測
- 審核發布
- 職務學習路徑

完成判準：

- 未審語音不可成為正式答案
- 每張知識卡有來源、審核者與版本

### Phase 5：企業系統串接與有限自動化

範圍：

- ERP／CRM／MES 讀取
- 核准後寫入
- 訂單、庫存、交期與客戶資料
- 高信心、低風險流程自動化

完成判準：

- 最小權限
- 冪等
- 可回滾
- 全程稽核
- 失敗時 fail-closed

### 12.1 MVP 目標

用一家製造業客戶、三種角色，證明「語音＋知識＋表單」真的能減少工作時間。

### 12.2 建議角色

- 業務
- 設備／現場人員
- 主管／審核者

### 12.3 MVP 功能

1. 手機登入與職務首頁

3. 來源文件與版本顯示
4. 掃設備 QR Code

- 完整離線原生 APP

## 13. 風險與控制

### 13.1 知識錯誤

風險：

- 版本過時
- OCR 錯誤
- 召回錯檔
- 非正式經驗覆蓋正式規範

控制：

- 權威分級
- 生效版本
- 來源引用
- 文件 owner
- 定期複核
- 證據不足拒答

### 13.2 語音辨識錯誤

風險：

- 料號、金額、數量誤聽

控制：

- 結構化確認
- 專有詞字典
- 關鍵欄位朗讀回確認
- 不以語音結果直接正式送出

### 13.3 生成內容不可靠

風險：

- AI 補寫不存在的條款或數字

控制：

- Fixed Form
- 來源驗證
- 欄位型別
- 規則計算
- 人工核准

### 13.4 權限與機密

風險：

- 業務看到研發配方
- 跨公司資料洩漏
- 語音錄音保存不當

控制：

- tenant／department／role
- object-level authorization
- 錄音保存期限
- 加密與稽核
- 最小權限

### 13.5 過度自動化

風險：

- 錯誤報價、錯誤工單或生產事故

控制：

- 依風險分級
- 預設草稿
- 正式流程需核准
- 安全相關只提供指引，不取代合格人員

## 15. 商業包裝建議

不要賣「RAG」、「向量資料庫」或「聊天機器人」，而應賣具體場景。

可包裝為：

- 製造業規格與 SOP 助理
- 業務報價與文件助理
- 設備維護知識助理
- 品質與客訴助理
- 新人訓練與經驗傳承助理

共同底層都是 Enclave；客戶購買的是職能模組、導入整理、表單與流程。

導入服務本身也是價值：

- 文件盤點
- 部門與權限整理
- 表單標準化
- 價格與作業規則整理
- Know-how 訪談
- 知識 owner 建立

這個過程類似 ISO 導入：不只是安裝軟體，也協助公司把原本沒有制度化的知識整理成資產。

## 16. 關鍵決策

本文件提出以下建議決策：

1. Enclave 保持通用知識核心，不在底層寫死製造業。
2. 商業定位聚焦製造業，以職能工作模組包裝。
3. 行動體驗採 Voice-first，但保留文字、選單、相機與掃碼。
4. 模組以工作場景定義，不只按部門分類。
5. 第一版所有正式文件預設人工確認。
6. 計算與交易規則由程式執行，不交給 LLM 自由計算。
7. 語音 know-how 必須審核後才可發布。
8. 先 PWA 驗證流程，再依離線與硬體需求決定原生 APP。
9. 第一批優先做「規格／SOP」、「報價草稿」、「異常／交接」。
10. Point B 未達成前，不宣稱可任意丟檔、任意問答或無人執行。

## 17. 最終結論

這個方向是正確、可行且與 Enclave 現有能力高度連續的。

真正的產品不應是：

> 在手機裡放一個可以講話的知識庫聊天框。

而應是：

> 使用者以語音、掃碼或拍照交代工作；系統依他的職務、權限與當下場景，取得公司知識、執行可驗證規則、補問必要欄位，產生符合公司格式的工作成果，再由人員確認或核准。

Enclave 已能支撐知識、權限、檢索、拒答、生成與來源驗證；下一步要補的是產品工作層，而不是重做知識底座。

因此最合理的演進路徑是：

```text
知識庫＋文字問答
→ 行動＋語音
→ 職務場景模組
→ Fixed Form＋規則計算
→ 審核工作流
→ Know-how 傳承
→ 企業系統串接與有限自動化
```

這會讓 Enclave 從「會回答的知識庫」成為「真正能協助製造業完成工作的知識作業平台」。
