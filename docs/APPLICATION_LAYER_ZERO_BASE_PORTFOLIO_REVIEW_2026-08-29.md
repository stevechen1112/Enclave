# 應用層零基盤點：現有功能存在性審查

**日期：** 2026-08-29  
**狀態：** 第一輪產品組合審查  
**適用範圍：** 現有 MKA、固定表單、通用生成與場景型前端功能  
**不包含：** 多租戶、Input、Asset、Knowledge、Evidence、問知識、權限、版本與治理等不可被應用反向綁定的產品核心

---

## 1. 這次審查要解決什麼

現有程式中已經有報價、異常、交接、日報、維修、8D、CAPA、師傅經驗、訓練、採購、請款、會議紀錄與報告生成等功能。

本次不問「如何改良這些功能」，而先問：

> 假設今天完全沒有這段程式，我們仍會選擇把它做成 Enclave 的應用模組嗎？

既有程式只能作為技術資產盤點，不能作為產品存在理由。第一輪審查不批准 UI 重做、不建立工程 Phase，也不因功能已部署就給予較高優先權。

---

## 2. 不變的產品核心

下列能力不進入應用存在性競賽，只能持續增強：

- 多租戶、帳號、租戶隔離與權限。
- 多元 Input：文件、表格、圖片、音訊、影片、網址、Connector 與外部紀錄。
- Asset、Artifact、Knowledge Unit 與 Evidence。
- 解析、OCR、ASR、影片理解、時間軸與品質信心。
- 有證據的問知識、檢索、拒答與回饋。
- 知識審核、發布、版本、有效日期、撤銷與治理。
- 稽核、用量、可觀測性、成本與安全護欄。
- Pack Runtime 及應用可插拔所需的穩定契約。

場景應用可以使用這些能力，但核心不得 import、辨識或依賴報價、異常、8D、師傅或任何租戶專屬業務名詞。

---

## 3. 第一輪審查標準

每個現有應用假設都以相同問題審查：

1. **企業問題是否普遍？** 是否跨多數企業存在，而非單一公司流程。
2. **成果是否清楚？** 使用後是否產生可量測的工作成果。
3. **是否放大核心價值？** 是否真正使用多元 Input、知識、Evidence 與治理，而非只借用登入與表單。
4. **是否可標準化？** 多數租戶能否直接啟用，只做少量設定。
5. **差異是否足夠？** 是否優於既有 ERP、MES、CMMS、QMS、LMS、CRM 或通用辦公工具的既有能力。
6. **導入條件是否合理？** 是否不需要大量客製、主資料與外部整合才能產生第一個價值。
7. **風險是否可控制？** 錯誤建議、權限、合規與操作風險能否被 Evidence 與人員確認控制。
8. **是否能獨立成模組？** 能否安裝、停用、封存、移除，而不影響核心與其他應用。
9. **是否有客戶證據？** 是否已有真實需求、資料、使用者與可驗收問題集。
10. **零基反事實是否成立？** 沒有既有程式時，是否仍值得投入。

現有程式碼完成度不列入價值分數；它只影響未來通過後的實作成本。

## 4. 第一輪可能結果

| 結果 | 定義 | 下一步 |
|---|---|---|
| 核心能力 | 本來就是產品核心，不應包成選配場景。 | 強化核心契約與體驗。 |
| 共通 Workflow | 多個應用共用的任務、表單、簽核、待辦或輸出能力。 | 抽回平台，不作為單獨銷售應用。 |
| 標準模組候選 | 問題普遍、核心槓桿高、少量設定即可使用。 | 進入需求與客戶驗證，不代表已核准開發。 |
| 產業／租戶假設 | 可能有高價值，但差異、風險或整合依賴高。 | 等待設計夥伴與真實證據。 |
| 退出應用目錄 | 不值得作為 Enclave 應用；可能保留為模板、內部元件或相容頁面。 | 不再新增產品投資，另行評估封存。 |

## 5. 先把不是應用的功能移出應用清單

| 現有功能 | 零基分類 | 理由 |
|---|---|---|
| 問知識 | 核心能力 | 是企業知識核心的通用使用介面，所有場景共用。 |
| 規格／SOP 查詢 | 核心專業模式 | 是問知識在設備、產品與版本範圍下的專業模式，不應獨立複製問答產品。 |
| 文件、圖片、錄音、影片匯入 | 核心能力 | 是 Input 與 Asset 管線。 |
| 訪談錄音、轉錄與候選萃取 | 核心能力 | 是長音訊 Input 與 Knowledge candidate 能力；是否形成傳承計畫是另一個應用問題。 |
| 影片步驟、時間碼與 SOP 衝突覆核 | 核心治理能力 | 屬於多模態知識建立與發布流程。 |
| 我的表單 | 共通 Workflow | 是使用者工作清單的一種 view，不是獨立應用。 |
| 審核匣 | 共通 Workflow | 多個應用與知識治理共同使用的決策入口。 |
| 任務引擎 | 共通 Workflow | 是應用執行骨架。 |
| 固定表單與公司版型 | 共通 Workflow／輸出能力 | 表單與輸出不是工作場景本身。 |
| 職能工作台 | 應用 Shell | 應顯示已安裝應用與待辦，本身不是業務應用。 |
| 模組、角色、模板、政策與 metrics 設定 | 租戶管理能力 | 是安裝與治理應用的管理介面。 |

## 6. 現有應用假設的第一輪審查

### 6.1 業務報價

**現有程式：** 語音／文字擷取客戶、料號、數量與價格，知識補值、稅額計算、表單、送審及匯出。

**零基判斷：** 報價需求普遍、結果可量測，但價格、MOQ、交期、折扣、客戶主資料、ERP 與核准規則高度依賴租戶。若沒有正式資料整合，容易退化成語音填表，無法形成足夠差異。

**第一輪結果：** **產業／租戶假設**。

**進入下一輪的必要證據：** 有設計夥伴願意提供報價流程、正式價格來源、歷史報價、版型與驗收指標，且核心知識與 Evidence 能顯著減少查找及重填時間。

### 6.2 現場異常回報／處置

**現有程式：** 異常任務、語音欄位、表單、QR 基礎、簽核、安全 policy 原型、交接與維修資料結構。

**零基判斷：** 問題普遍且可高度運用多模態 Input 與知識，但異常類型、設備、責任、安全與既有 CMMS／MES 差異很大。通用 AI 排除異常的承諾不可行；只有在有限設備、已核准 SOP 與真實歷史案例下，受控處置輔助才可能成立。

**第一輪結果：** **產業／租戶假設**，不是既定第一場景。

**進入下一輪的必要證據：** 單一租戶、有限設備族群、高頻可控異常、正式文件、現場專家及可量測的回報／接手／解決基準。

### 6.3 交接班

**現有程式：** 獨立任務與固定交接表單。

**零基判斷：** 交接普遍，但單獨數位化交接表的差異很弱。它更合理地作為未完成工作、異常、任務與設備狀態的轉移機制，而非獨立應用。

**第一輪結果：** **共通 Workflow／其他應用元件**。

### 6.4 工作日報

**現有程式：** 獨立任務與固定日報表單。

**零基判斷：** 日報普遍，但市場替代品多，人工再填一次的價值低。真正有意義的是從已發生的任務、事件與產出自動彙整，再讓使用者補充。

**第一輪結果：** **共通輸出能力／其他應用元件**，不作為獨立應用。

### 6.5 設備維修

**現有程式：** 固定設備維修表單，另有未正式接入的事件、附件與任務原型。

**零基判斷：** 需求普遍，但完整維修管理涉及資產台帳、保養、工單、零件、工時、供應商與 CMMS／EAM 整合。現有核心只有在「文件與經驗輔助維修」上有差異，尚不足以支撐完整維修應用。

**第一輪結果：** **產業／租戶假設**；現有表單不構成產品。

### 6.6 品質 8D

**現有程式：** 8D 任務、固定欄位、簽核與輸出骨架。

**零基判斷：** 製造業問題清楚、Evidence 與歷史案例高度相關，但不是任何企業都使用同一流程；QMS 市場已有成熟工具。差異必須來自多模態客訴／檢驗證據、根因資料與改善知識閉環，而不是把 8D 表格搬上網頁。

**第一輪結果：** **產業模組候選，需客戶驗證**。

### 6.7 CAPA

**現有程式：** 固定 CAPA 追蹤表單。

**零基判斷：** CAPA 不是獨立入口價值，應是品質事件、稽核或 8D 後續的責任、期限與有效性驗證。

**第一輪結果：** **品質應用元件**，不作為獨立應用。

### 6.8 師傅經驗／專家知識傳承

**現有程式：** Know-how 卡、訪談、長錄音、轉錄、審核、SOP 衝突與已核准知識 provider。

**零基判斷：** 人員流動、經驗流失與難以將影音轉為可治理知識是廣泛企業問題，也最直接使用 Enclave 的 Input、Knowledge、Evidence 與 Review 核心。但「錄音與萃取」本身屬於核心；真正可能成為應用的是有目標、有負責人、有覆核與完成度的知識傳承計畫。

**第一輪結果：** **標準模組候選，進入問題／客戶驗證**。

**需避免：** 因現有程式較完整就直接批准。仍需證明企業願意持續使用、覆核成本可控，且成果比一般錄音摘要或文件管理更有價值。

### 6.9 新人訓練

**現有程式：** training 任務與訓練 Checklist。

**零基判斷：** 新人上手是普遍問題，且企業知識可以直接轉化為必讀、情境題與工作指引。但完整 LMS 已有成熟市場；Enclave 的合理範圍是「依企業最新知識生成並追蹤工作上手」，不是課程、證照、排課與人資系統大全。

**第一輪結果：** **標準模組候選，可能與知識傳承合併驗證**。

### 6.10 採購單

**現有程式：** 固定採購表單。

**零基判斷：** 採購普遍，但主價值在 ERP、供應商、庫存、預算、驗收與會計整合；目前只使用表單能力，沒有顯著放大 Enclave 核心。

**第一輪結果：** **退出應用目錄**；Schema 可暫作通用模板或相容資料，不再當成產品應用。

### 6.11 請款單

**現有程式：** 固定請款表單。

**零基判斷：** 與會計、憑證、預算、發票及 ERP 高度耦合，現有功能沒有核心差異。

**第一輪結果：** **退出應用目錄**。

### 6.12 會議／拜訪紀錄

**現有程式：** 固定表單與通用會議記錄生成。

**零基判斷：** 問題普遍但替代品極多。除非它是某個有後續閉環的專屬場景元件，否則不值得作為 Enclave 獨立應用。

**第一輪結果：** **退出應用目錄**；可保留為 Input／輸出模板。

### 6.13 函件、摘要、會議記錄、分析報告與 FAQ 生成

**現有程式：** 通用 Generate／Reports 頁面及五種輸出類型。

**零基判斷：** 這些是輸出格式，不是業務應用。若由有權限的企業知識與 Evidence 生成，可成為核心內容產出能力；獨立列成多個應用沒有合理邊界。

**第一輪結果：** **核心輸出能力或舊有相容頁面**，移出應用目錄後另行決定是否重做或封存。

## 8. 第二輪應先驗證什麼

目前最符合核心、且可能跨企業標準化的假設是：

> 將企業分散在老師傅、錄音、影片與文件中的知識，經過人員覆核後，轉化為特定工作或新人可實際完成的知識傳承與上手計畫。

下一輪不應先畫完整 UI，而要驗證：

- 哪一種企業知識最容易流失且損失明確。
- 誰負責發起、受訪、覆核及使用。
- 從錄製到正式發布需要多少人工成本。
- 成果是知識卡、工作指引、訓練任務，還是其他形式。
- 使用者是否真的會在工作中回來查閱。
- 是否縮短新人上手、降低重複詢問或保存關鍵經驗。
- 哪部分是核心 Input／Knowledge，哪部分才是可卸載應用。

品質 8D、異常處置與報價可以並行保存為訪談題目，但沒有設計夥伴與真實資料前不進入工程設計。

## 9. 應用模組的硬性架構 Gate

任何候選通過產品驗證後，仍需符合：

1. 核心不 import 該應用的 model、service、route 或業務名詞。
2. 應用只透過版本化 contract 使用 Input、Knowledge、Evidence 與 Workflow。
3. 應用擁有自己的 manifest、前端 route、API、task handler、設定與測試。
4. 資料所有權、保留、匯出、封存與刪除政策明確。
5. 租戶可獨立安裝、停用、封存與移除。
6. 停用後 route、API、背景工作、導航、檢索 provider 與 action 全部 fail closed。
7. 移除應用不影響核心或其他應用。
8. 租戶標準設定保持簡單；進階差異由我們協助或透過 extension 完成。
9. 必須有產品驗收、權限、跨租戶、升降版與卸載測試。
10. 每個完整 Phase 完成 code review 後才可進下一階段。

---

## 10. 對既有程式的處理原則

- 本文件不授權刪除任何現有程式或租戶資料。
- 退出應用目錄代表停止把它當成產品應用，不等於立即刪除相容能力。
- 通過驗證的應用可以重用既有程式，但必須重新符合模組邊界。
- 未通過的程式可以保留為模板、測試 fixture、遷移相容層或待封存功能。
- 任何實際移除都需要依賴分析、資料生命週期、遷移與回復方案。

---

## 11. 本階段結論

第一輪沒有批准任何既有場景直接進入實作。

最值得進入下一輪驗證的是「知識傳承計畫」與「知識驅動的新人上手」，因為它們最直接放大多模態 Input、Knowledge、Evidence 與 Review 核心；但仍須從真實企業成果出發，不因現有 Know-how／training 程式而自動成立。

異常、品質與報價仍有可能成為高價值模組，但目前只保留為需要設計夥伴與資料的假設。交接、日報、CAPA、表單與審核則應回到其他應用或共通 Workflow 的正確位置。採購、請款、會議紀錄與通用報告不再被當作獨立應用。

這才是應用層真正的零基重建：核心持續增強，應用是否存在則必須重新證明。

## 12. 本階段 Code Review 結果

本階段只完成產品組合的零基重新分類，沒有修改 runtime、API、資料庫、租戶資料或 production 行為。

Review 已直接對照現行程式並確認：

- `app/services/mka_module_seed.py` 目前 seed 5 個模組：`spec_sop`、`sales_quote`、`incident_handover`、`quality_8d`、`training_knowhow`。
- 同一檔案目前定義 8 個 canonical 任務：`quote`、`incident`、`handover`、`quality_8d`、`interview`、`ask`、`training`、`daily_report`。
