# 場景 01：有證據的企業知識問答／SOP 決策支援

**日期：** 2026-08-29  
**狀態：** 場景重新定義草案（尚未代表 UIUX 與實作全部完成）  
**所屬：** 核心知識產品；`spec_sop` 提供製造業規格／SOP 專業模式  
**目的：** 先回答「這個應用是誰」，再以十項完整場景問題檢查現況並建立建議預設值。

---

## 1. 這個應用是誰

### 正式名稱

**有證據的企業知識問答／SOP 決策支援**

使用者介面可簡稱：**問知識**。

### 一句話定義

讓企業人員在正確權限、職能與適用範圍內，快速取得可以回到正式來源、知道適用版本、知道不確定性，並在風險過高時會拒絕武斷作答的工作答案。

### 它不是什麼

- 不是開放式通用聊天機器人。
- 不是只列出搜尋結果的文件搜尋器。
- 不是正式 SOP 的替代品，也不會把 AI 生成內容自動視為公司政策。
- 不是機台控制系統，不直接啟動、停機、復歸或修改參數。
- 不是核准者；高風險作業仍由正式文件、合格人員與主管決策。
- 不是內容管理後台；一般使用者不必理解 chunk、embedding、provider 或索引等技術名詞。

### 核心承諾

```text
知道 → 用可驗證的證據回答
不確定 → 說明缺少什麼並引導補充
無權限 → 不洩漏內容，也不暗示敏感資料存在
版本不明 → 先確認適用設備／產品／版本
風險過高 → 引用正式 SOP、顯示警告並要求合格人員介入
```

## 2. 誰使用這個應用

### 主要使用者

| 使用者 | 常見問題 | 預期價值 |
|---|---|---|
| 現場操作員 | 怎麼操作、這個警報代表什麼、下一步先確認什麼 | 降低查文件時間與用錯版本的機率。 |
| 設備／維修人員 | 機台規格、維修步驟、歷史處置及禁止事項 | 快速定位適用設備與正式維修依據。 |
| 品保人員 | 檢驗規格、允收範圍、版本差異及過去案例 | 降低錯用規格與重複調查。 |
| 業務／產銷人員 | 產品規格、MOQ、交期政策及客戶適用版本 | 在權限範圍內快速找到對外回覆依據。 |
| 班長／師傅 | SOP、師傅經驗、異常判斷及新人說明 | 將正式規範與已審經驗一起使用，但不混為同一權威。 |
| 新人 | 名詞、必讀 SOP、工作步驟及常見錯誤 | 降低上手門檻，知道何時必須求助。 |
| 主管 | 政策依據、跨部門資訊、版本差異與決策證據 | 快速檢查依據，不必逐份翻找文件。 |

### 次要使用者

| 使用者 | 在本場景中的責任 |
|---|---|
| 知識負責人 | 處理無法回答、錯誤來源、錯誤版本與內容缺口。 |
| 文件／SOP 審核者 | 確保只有適用、有效且已核准內容能作為正式依據。 |
| 租戶管理者 | 設定角色、部門、資料範圍、模組、保留期限與用量。 |
| 產品／系統維運人員 | 監控延遲、錯誤、索引品質及 provider degradation，不接觸無權限內容。 |

### 不應使用或不可使用者

- 未登入或未驗證的外部人員。
- 沒有 `ask` capability 的帳號。
- 沒有來源文件權限的人員。
- 企圖透過問答繞過部門、資料分類或租戶隔離的人員。
- 需要直接控制設備或批准高風險動作的人員；本應用只能提供決策支援。

### 現有權限設定與建議

現況：`owner`、`admin`、`hr`、`employee`、`viewer` 都具有核心 `ask` capability；MKA `spec_sop` 模組另宣告 `owner`、`admin`、`employee` 為 allowed roles。兩者目前不是完全一致。

建議預設：

- 核心「問知識」由 `ask` capability 控制，唯讀 viewer 也可詢問其有權看到的知識。
- `spec_sop` binding 決定是否出現規格／SOP 專業入口與專用工具，不應改變底層文件權限。
- 真正可回答的內容永遠由租戶、部門、角色、資料分類、文件 ACL、適用情境與版本共同決定。
- Job Role 用於改善入口、語言及適用範圍，不得取代安全權限。

## 3. 這個應用何時被使用

### 建議的主要進入時機

1. 使用者主動想查一個企業問題。
2. 從設備 QR、工單、產品、客戶或場景頁帶入脈絡後詢問。
3. 在異常回報、報價、8D、訓練等其他場景中需要查正式依據。
4. 新人閱讀知識時，需要追問或理解術語。
5. 主管審核一項工作時，需要核對原始規範。
6. 系統偵測到來源衝突、版本不明或知識缺口時，引導知識負責人處理。

### 不應使用的時機

- 緊急危害已發生而正式緊急程序要求立即停機、撤離或通報時；應先執行正式程序。
- 使用者要求系統直接控制設備、修改正式資料或代表主管核准時。
- 無法確認設備、產品或版本，而錯用答案可能造成安全、品質或財務風險時。

## 4. 十項場景問題：現況、建議與租戶設定

| 檢視問題 | 現有設定／能力 | 建議預設 | 租戶導入時要確認 |
|---|---|---|---|
| 1. 誰在什麼時候進入？ | 所有具有 `ask` capability 的角色可進入；也可由工作台、語音或帶 scene 的網址進入。 | 所有授權員工皆可問；依職能顯示範例與預設範圍。設備／產品相關問題優先從 QR 或場景深連結進入。 | 哪些角色能問、哪些部門資料可見、哪些場景必須先掃碼。 |
| 2. 要完成什麼工作？ | 現況支援問答、追問、對話歷史、來源與建議問題；`spec_sop` 宣告規格查詢、版本比較、SOP 步驟。 | 完成定義是「得到有適用範圍及證據的答案」或「明確知道為何不能回答及下一步」。 | 首租戶最重要的 20–50 類問題、回答格式與不可回答範圍。 |
| 3. 能從哪些 Input 帶入？ | 查詢文字、scene context、module key；工作台語音確認後可帶入問題。知識來源可包含文件、表格、圖片 OCR、音訊與影片產物。 | 第一版直接支援文字、語音、QR／場景；照片或影片提問先經統一 Input 管線成為可治理資產，不直接繞過權限與審核。 | 現場最常用的裝置、語音語言、設備 QR、料號及文件來源。 |
| 4. 缺資料如何補齊？ | 有追問建議及無證據／無權限／處理中／系統不可用等空答案狀態；尚無完整的結構化澄清流程。 | 設備、產品、版本、廠區或時間有歧義時，先問一個最關鍵的澄清問題；高風險問題不得猜測。 | 必須確認的識別欄位、常見別名及公司版本規則。 |
| 5. AI、正式來源、人工確認如何分開？ | 回答與證據分區；證據可顯示版本、頁碼、章節、工作表、列、逐字稿時間、生效日、適用範圍及相關度。 | 明確標示「AI 彙整」「正式文件」「已審經驗」「外部參考」；相關度不得當成答案正確率。作業與高風險回答必須引用有效正式來源。 | 哪些文件等級可作為正式依據、Know-how 的權威順位及誰能核准。 |
| 6. 完成後產生什麼？ | 產生串流回答、證據、追問建議、對話歷史、回饋及可複製引用。 | 預設輸出直接答案、適用範圍、必要步驟、警告、證據與下一步。問答本身不自動成為正式知識或執行動作。 | 是否需要儲存、分享、匯出或轉成任務；對話保留期限。 |
| 7. 是否送審、退回、追蹤或通知？ | 一般問答不用送審；來源知識另有發布審核。負面回饋可進管理者處理佇列。 | 查詢不送審；知識發布必須治理。錯誤、版本錯誤、無法回答與高風險疑問可建立知識改善待辦並通知責任人。 | 回饋 SLA、責任人、通知方式及高風險升級路徑。 |
| 8. 如何回到正式證據？ | Evidence drawer、證據卡、文件 deep link、版本／頁碼／工作表／列／時間資訊與引用複製已存在。 | 重要主張應與對應證據可一鍵互相定位；顯示版本、生效日、適用範圍及衝突。影片應直接跳時間點。 | 文件檢視權限、舊版顯示方式、影片及外部系統 deep link。 |
| 9. 手機、平板、桌機是否適用？ | A 款問答頁為響應式設計；歷史為抽屜，Evidence 在桌機為右側、手機為底部覆蓋層。 | 桌機適合比較證據；平板／手機提供大按鈕、直接語音、QR 與單手操作。保密內容預設不做離線快取。 | 廠內網路、瀏覽器、相機／麥克風政策、字級及無障礙需求。 |
| 10. 成效如何量測？ | 已有查詢量、已答／未答、延遲、熱門問題、負面分類、回饋率與無答案清單；模組宣告追蹤 task completion、evidence gaps。 | 加入解決率、證據覆蓋、錯版本率、拒答正確性、權限洩漏、引用有效性及搜尋到解決時間。 | 基準期、成功門檻、抽樣覆核責任與試行期間。 |

## 5. 建議的標準使用者旅程

```text
入口
  → 帶入使用者權限、職能與可選 scene
  → 使用者文字／語音提問
  → 判斷意圖、歧義與風險
  → 必要時只追問一個最關鍵問題
  → 限定租戶、權限、設備／產品、版本與有效日期
  → 檢索可存取的知識來源
  → 檢查證據是否足以支撐回答
  → 產生回答、適用範圍、警告、證據及下一步
  → 使用者查看來源／追問／回饋
  → 錯誤或知識缺口進入治理待辦
```

### 建議回答畫面結構

1. **直接回答**：先讓使用者看懂答案，不先展示系統過程。
2. **適用範圍**：廠區、產線、設備、產品、版本、日期或角色。
3. **步驟或比較**：只有問題需要時才出現。
4. **重要警告**：禁止事項、停機條件、需要主管或維修介入的條件。
5. **證據**：文件名稱、版本、頁面／章節／列／時間碼與內容片段。
6. **不確定性**：缺少的版本、設備或其他必要資料。
7. **下一步**：追問、打開正式文件、重新限定範圍或回報知識缺口。

## 6. 問題風險分級

現況 `ask` TaskDefinition 將整個任務標為 `low` risk。這不足以表達「名詞解釋」與「機台復歸」的風險差異。

建議改為每次問題動態分級：

| 等級 | 例子 | 建議行為 |
|---|---|---|
| R0 資訊查詢 | 某縮寫是什麼、文件在哪裡 | 有企業證據即可回答；顯示來源。 |
| R1 工作指引 | SOP 步驟、規格範圍、版本差異 | 必須有適用且有效的來源；顯示版本與範圍。資料不完整時先澄清。 |
| R2 高風險決策支援 | 復歸、解除安全裝置、修改關鍵參數、品質放行 | 只依有效正式 SOP／政策回答；醒目警告，不自由補步驟；必要時要求停下並聯絡合格人員或主管。 |

任何等級都不得因使用者無權限而引用被隔離內容。R2 找不到合格證據時必須拒答，而不是用相似文件拼湊答案。

## 7. Input 與知識來源邊界

### 查詢 Input

第一版建議正式支援：

- 鍵盤文字。
- Push-to-talk 語音，先顯示逐字稿供確認。
- QR／條碼帶入設備、產品、料號、工單或場景。
- 從其他場景帶入結構化 context。

後續支援：

- 拍攝警報畫面、銘牌或瑕疵照片後提問。
- 錄製短影片或異常聲音後提問。

照片、音訊與影片必須先走統一 Intake、雜湊、權限、掃毒、解析、信心及證據流程；不能把臨時附件直接交給模型後繞過企業治理。

### 可回答的知識來源

- 已發布的正式 SOP、規格、政策與手冊。
- 仍在有效期且適用範圍正確的版本。
- 已核准且未逾複查日的 Know-how。
- 租戶允許的外部參考資料，但必須標示權威較低。
- 從圖片、音訊及影片產生、經覆核發布的知識單元與 Evidence。

草稿、撤銷、過期、未核准或無權限內容不能用來支持正式答案。

## 8. 現有設定保留與調整建議

### 建議保留

- `knowledge_scope_policy.doc_types = [sop, spec]` 作為 `spec_sop` 專業模式預設。
- `require_version = true`。
- `require_version_citation = true`。
- 支援 `lookup_spec`、`compare_versions`、`sop_steps` 三個明確 intent。
- 場景、module 與 ACL 的檢索篩選。
- 回答串流、對話歷史、Evidence drawer、空答案分類及回饋分類。
- 版本、頁碼、章節、工作表、列、逐字稿時間、生效日與適用範圍 locator。

### 建議調整

1. **統一核心 Ask 與 `spec_sop` 的角色規則**：以 `ask` capability 加來源 ACL 為主，module binding 只控制專業能力與入口。
2. **問題級風險分類**：取代整個 ask 固定 low risk。
3. **加入澄清狀態**：缺設備、產品或版本時，先澄清再回答。
4. **語音直接進問答頁**：不只從 `/job` 間接進入；仍需逐字稿確認。
5. **證據與主張對齊**：重要段落或步驟能直接定位到支持它的來源。
6. **正式性標籤**：區分正式 SOP、正式規格、已核准案例、已審 Know-how 與外部參考。
7. **處理知識缺口**：負面回饋、無答案及錯版本能形成有 owner 與狀態的治理工作。
8. **避免固定 top-k 語意混亂**：目前 ChatRequest 預設呈現 `top_k = 3`，模組另有 `max_context_chunks = 8`。建議明確區分候選召回上限、模型上下文上限與畫面顯示證據數，並用評測校準，不以單一數字同時代表三件事。

## 9. 完成、拒答與失敗定義

### 成功完成

- 使用者得到直接且可理解的答案。
- 重要事實有可存取證據。
- 適用版本與範圍清楚。
- 風險與禁止事項有清楚提示。
- 使用者能打開原始來源或繼續追問。

### 正確拒答也算成功

- 沒有足夠證據。
- 文件仍在處理或審核。
- 使用者沒有權限。
- 設備、產品或版本無法確認。
- R2 高風險問題沒有有效正式來源。
- 系統或檢索服務暫時不可用。

拒答必須說明可採取的下一步，但不得洩漏無權限資料的名稱或內容。

### 真正失敗

- 無證據卻給出確定答案。
- 使用錯誤或過期版本。
- 引用內容與回答不一致。
- 洩漏其他租戶、部門或資料分類內容。
- 將 Know-how 誤標為正式 SOP。
- 高風險問題未警告或自行補出危險步驟。
- 有正確資料卻持續拒答且無法被治理流程發現。

## 10. 建議成效指標

### 現有可沿用指標

- 查詢量與使用人數。
- 已回答／無答案比例。
- 平均延遲與趨勢。
- 熱門問題。
- 正面／負面回饋及負面分類。
- 無答案問題清單。
- Retrieval provider 與 degradation 狀態。

### 應新增的產品指標

| 指標 | 定義 |
|---|---|
| 問題解決率 | 不需改問或人工搜尋，即取得可採用答案的比例。 |
| 證據覆蓋率 | 可執行或企業事實回答中，有有效 Evidence 支持的比例。 |
| 引用定位有效率 | 點擊後能打開正確文件版本與位置的比例。 |
| 錯版本率 | 回答引用不適用、撤銷或過期版本的比例。 |
| 正確拒答率 | 缺證據、缺權限或高風險資訊不足時，系統正確停止的比例。 |
| 錯誤拒答率 | 明明有可用證據卻沒有回答的比例。 |
| 搜尋到解決時間 | 從送出問題到使用者取得足以採取下一步資訊的時間。 |
| 人工轉介率 | 必須交由師傅、主管或知識負責人處理的比例。 |
| 知識缺口關閉時間 | 無答案或錯誤回饋從建立到修正發布的時間。 |
| 權限洩漏事件 | 必須為 0。 |

在第一個租戶取得基準資料前，不先虛構一般性好評率或節省時間目標。安全與正確性 Gate 則可先固定：權限洩漏為 0；R2 無正式證據時不得提供確定作業指令；受控驗收集中不得引用撤銷或錯誤版本。

## 11. 裝置與環境要求

### 桌機

- 適合較長問題、版本比較及多份證據並排。
- 主答案保持聚焦，對話歷史與 Evidence 為次要抽屜。

### 平板

- 可在產線旁查看步驟、圖片與文件。
- 重要按鈕要可觸控，橫向與直向皆可使用。

### 手機

- 支援單手文字、直接語音、掃碼及開啟 Evidence。
- Evidence 使用底部或全螢幕抽屜，避免三欄壓縮。
- 高風險警告不因小螢幕被收起。

### 現場環境

- 語音需在噪音與口音條件下驗證。
- 斷線時不得把半個回答誤認成完成答案。
- 機密問答預設不離線快取。
- 相機、麥克風被拒絕時仍可手動輸入。

## 13. 場景完成驗收條件

這個場景不能因為頁面能回答問題就算完成。至少需要：

1. 六種主要職能的入口與權限行為符合設定。
2. 文字、語音與 QR／scene 三條主要入口均能完整帶入查詢。
3. 規格查詢、版本比較、SOP 步驟、無答案、無權限、來源處理中及系統降級都有驗收案例。
4. R0、R1、R2 風險行為有明確測試，R2 無正式證據時 fail closed。
5. 每項重要事實可回到有權限的正確來源與位置。
6. 撤銷、過期、錯版本、跨租戶及跨部門資料不會被引用。
7. 桌機、手機與平板完成瀏覽器走查。
8. 語音失敗、相機／麥克風拒絕、斷線與重新登入有清楚恢復方式。
9. 負面回饋與無答案可進入治理流程並指派處理。
10. 以首租戶真實問題集建立 baseline，再決定商業成效門檻。
